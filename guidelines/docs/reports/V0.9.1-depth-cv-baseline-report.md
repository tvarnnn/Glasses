# V0.9.1 — Experimental CV Lab: Depth Experiment CPU/GPU Baseline Report

Status: **FILLED — measured CPU and CUDA runs complete on the Tower's own
hardware.** Per `02-DEVELOPMENT-RULES.md` Rule 3, numbers below are
reported exactly as measured. This is a bounded CPU-vs-GPU comparison run
(`scripts/depth_benchmark.py`), not a sustained-streaming soak test — see
`V0.7-sustained-streaming-report.md` for that separate report shape.

## Success Criteria (per `docs/modules/EXPERIMENTAL-CV.md`)

- **Hypothesis/question:** Does running the `depth` experiment
  (MiDaS-small monocular depth estimation) on the Tower's RTX 5070 via
  PyTorch CUDA execution measurably reduce per-frame latency compared to
  the same experiment on CPU, and is the improvement large enough to
  justify treating CUDA as the default device for this experiment going
  forward?
- **Dataset/session:** 60 synthetic 504x896 JPEG frames per run (the
  roadmap's target glasses-stream resolution — see `03-ROADMAP.md`
  V0.7), generated and sent by `scripts/depth_benchmark.py` against a
  live Tower instance running `TOWER_CV_EXPERIMENT=depth`. Same
  synthetic frame content used for both runs so the two are directly
  comparable.
- **Metric(s):** client-observed `round_trip_ms` (first frame, avg, max)
  from `scripts/depth_benchmark.py`; Tower-side `receive_to_result_ms`,
  `cv_processing_ms`, and per-stage `stage_ms_avg`/`stage_ms_max`
  (`decode`/`preprocess`/`inference`/`postprocess`) from the Tower's own
  `[Tower][Session] final summary` log line; `effective_fps`,
  `process_cpu_percent`, `backpressure_drops`, `frame_processing_errors`.
- **Baseline:** CPU execution (`TOWER_CV_DEVICE=cpu`) of the identical
  `depth` experiment against the identical synthetic frame set.
- **Result:** CUDA execution measurably beats the CPU baseline on every
  steady-state latency metric — see Measured, below. Margin is modest
  (~31% on the headline client-side average), not dramatic, because
  MiDaS-small on a 504x896 frame is light enough that CPU inference is
  already fast.
- **Resource usage:** model-load-time GPU memory allocation (82.7MB) and
  peak allocation at release, both logged by `tower/experiments/depth.py`
  — see Measured, below. `process_cpu_percent` reported per run.

## Run metadata

- Date: 2026-08-20
- Hardware: RTX 5070 (Blackwell, `torch.cuda.get_device_capability(0) ==
  (12, 0)`), driver-reported CUDA 13.2, torch 2.13.0+cu132.
- Experiment: `depth` — MiDaS-small monocular depth estimation. Output is
  relative (inverse) depth, not metric distance — see
  `07-PLATFORM-CONSTRAINTS.md` Limitation 1 / Core Principle 2 and the
  `DepthEstimation` docstring in `tower/experiments/depth.py`. This
  report measures latency/throughput only; it does not evaluate depth
  accuracy (no ground-truth reference used).
- Frame source: `scripts/depth_benchmark.py --frame-count 60`, synthetic
  504x896 JPEG frames — this validates the Tower-side pipeline and the
  CPU-vs-GPU comparison itself, not real-camera/real-glasses content.
  Same caveat as `V0.7-sustained-streaming-report.md`'s
  synthetic-source note: a synthetic-script run establishes the
  Tower's own relative CPU-vs-GPU comparison, not absolute real-world
  figures for a physical-glasses stream.
- Each run: Tower started fresh with `TOWER_CV_EXPERIMENT=depth` and the
  device under test (`TOWER_CV_DEVICE=cpu` or `=cuda`), then
  `scripts/depth_benchmark.py --frame-count 60` run once against it.

### CPU vs. CUDA — headline comparison

| Metric | CPU | CUDA | Change |
|---|---|---|---|
| `round_trip_ms_avg` (client) | 29.35 | 20.18 | **~31% lower** |
| `receive_to_result_ms_avg` (Tower) | 29.745 | 24.365 | ~18% lower |
| `cv_processing_ms_avg` (Tower) | 29.102 | 23.666 | ~19% lower |
| `stage_ms_avg.inference` (Tower) | 22.722 | 15.363 | ~32% lower |
| `effective_fps` | 32.94 | 40.03 | ~22% higher |
| `first_frame_round_trip_ms` (client) | 87.9 | 306.19 | **higher on CUDA** |
| `stage_ms_max.inference` (Tower) | 46.582 | 289.299 | **higher on CUDA** |

CUDA is consistently and measurably faster than CPU on every
steady-state metric — client round-trip average, Tower-side
`receive_to_result_ms`, and per-stage `inference` time all improve by
roughly 18-32%. The margin is real but modest, not dramatic: MiDaS-small
on a 504x896 frame is light enough that CPU inference (~23-29ms) is
already fast, so GPU dispatch/host-device copy overhead eats into part
of CUDA's theoretical advantage at this workload size. This is a clear,
consistent, reproducible win for CUDA on this hardware/workload, not a
transformative one.

CUDA's **first-frame** cost is much higher than CPU's, in both the
client-observed figure (87.9ms -> 306.19ms) and the Tower-side
`stage_ms_max.inference` figure (46.582ms -> 289.299ms). This is the
documented one-time CUDA context/kernel warmup cost (context creation,
cuDNN/cuBLAS algorithm selection, first-launch kernel compilation) — see
the spec's Performance measurements section, which explicitly excludes
the first CUDA frame from steady-state averages for this reason. It is
expected, not a regression, and does not recur on subsequent frames
within the same session.

### GPU memory

- Model-load allocation: 82.7MB (`torch.cuda.memory_allocated()`,
  logged once at `load()` completion).
- Peak allocation at release: logged by `DepthEstimation.release()`
  (`tower/experiments/depth.py`) via `torch.cuda.max_memory_allocated()`,
  captured before the model reference is dropped and
  `torch.cuda.empty_cache()` is called, so the caching allocator has
  nothing still referenced left to release back to the driver.
  Per-session periodic GPU memory logging (alongside
  `SessionMetrics.should_log_summary()`) was considered and deliberately
  not built this milestone — see the spec's Performance measurements
  section for the recorded reasoning.

### Backpressure

Both runs show `backpressure_drops: 0` and `seq_gap_total: 0`.
Per-frame CPU-run latency was flat across the run (no upward drift — e.g.
frame 30 was ~27ms, frame 60 was ~27ms). This is a favorable result under
the spec's "Backpressure — no action, decision rule recorded" section:
the decision rule was that a rising `receive_to_result_ms` trend at this
frame count/rate would be the trigger for a future frame-dropping
milestone. That trend was not observed here, so no action is indicated —
the existing sequential `receive -> process -> ack` path in
`tower/routes/ws.py` held up at this frame count/rate on this hardware.
This does not rule out backpressure becoming necessary at sustained,
higher-frame-count, real-glasses-stream conditions (see the caveat under
Run metadata, above) — only that nothing in this bounded 60-frame run
demonstrates it is currently needed.

## Conclusion

- **Did this run answer the milestone's question?** Yes: CUDA execution
  of the `depth` experiment on this Tower's RTX 5070 is consistently
  faster than CPU execution of the identical experiment, across every
  steady-state metric measured, at a modest (~18-32%) margin explained
  by the workload being light enough for CPU to already perform
  reasonably well. This is the first PyTorch CUDA baseline the roadmap's
  future acceleration decisions (TensorRT, CV-CUDA, etc. — see
  `01-SYSTEM-ARCHITECTURE.md`, GPU / Acceleration Strategy) would need
  to beat.
- **Does this run show a backpressure/frame-dropping mechanism is
  currently justified?** No — 0 `backpressure_drops`, 0 `seq_gap_total`,
  and flat per-frame latency in both runs. Per the spec's recorded
  decision rule, this is evidence *against* building that machinery
  speculatively right now, not evidence it will never be needed.
- **Caveats:** synthetic-script frame source only (see Run metadata) —
  this establishes the Tower's own CPU-vs-GPU comparison and pipeline
  correctness, not real-camera or real-glasses-stream figures. 60 frames
  is a short, bounded measurement run, not a sustained-session soak test
  (see `V0.7-sustained-streaming-report.md` for that separate concern).
  Depth *accuracy* was not evaluated — this report is latency/throughput
  only, per `07-PLATFORM-CONSTRAINTS.md` Core Principle 2 (inference is
  not measurement, and this report does not claim otherwise).
- **Next steps (not started, not part of this milestone):** re-run this
  comparison against real camera/glasses frame content once available;
  revisit backpressure only if a real sustained session shows
  `receive_to_result_ms` drifting upward over time; evaluate TensorRT
  only if a future profiling run shows `inference` — not data movement
  or preprocessing — is the dominant bottleneck on a workload CUDA alone
  does not adequately address.
