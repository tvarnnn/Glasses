### seq_gap_total (raw sequence-number discontinuity count)
**This is NOT "frames lost in transit."** It is a raw, causally-neutral
count of discontinuities in the received `seq` field — nothing more.

Confirmed 2026-08-19: the iOS sender assigns `seq` from the DAT/source
capture-frame index (`frameCount` of incoming VideoFrames), but only
forwards roughly 1-in-30 of them by design (a throttled capture ->
transmit branch), so the Tower normally receives `seq` like
1, 30, 60, 90, ... under completely normal, healthy operation. Under the
current wire protocol (`seq, width, height, format, data` — no separate
transmission-attempt counter), a gap in `seq` cannot be attributed to any
single cause: it may be intentional sender-side sampling, a sender-side
drop, or genuine network/transit loss, and all three look identical on
the wire. **Do not report this number as network loss** in any summary
of this run. See `07-PLATFORM-CONSTRAINTS.md` Limitation 9 for the
future `source_seq` (original DAT/capture frame index) /
`tx_seq` (dense counter per frame message actually transmitted) protocol
split that would be required to actually distinguish these causes — not
implemented as of V0.7 (deliberately: V0.7 does not change the wire
protocol).
- Measured (raw count, cause unattributable): not provided in this handoff — pull the exact `seq_gap_total` value from the Tower's own final-summary log line if needed; given 695 frames received at the confirmed 1-in-30 throttle, a raw gap total in the low thousands would be expected and unremarkable (see the 2026-08-19 finding above).

## Mock/iPhone-camera vs. physical-glasses caveat

Per `07-PLATFORM-CONSTRAINTS.md` Limitation 12: a run whose frame source
above is `synthetic-script` or `mock-device-kit` validates the Tower-side
plumbing (instrumentation correctness, sustained-connection stability)
only. It does **not** establish real-world FPS, bandwidth, latency, or
drop-rate figures — those require `iphone-camera` (for real BLE/WiFi
transport behavior) and ultimately `physical-glasses` (for real optics,
RF, thermal, and battery figures). Label every number above with which
source produced it, and do not present a `synthetic-script` or
`mock-device-kit` run as satisfying V0.7's real target measurement.

**This run's status: mock/iPhone validation only. Physical-glasses
validation is explicitly deferred — not yet performed, no target date
set.** Everything measured above (instrumentation correctness, clean
`stream_start`/`stream_stop` lifecycle behavior, 0 backpressure drops,
low latency/resource usage, clean `stream_stop` finalization) confirms
the Tower-side pipeline and V0.7 measurement plumbing work correctly end
to end. None of it confirms real optics, real Bluetooth/Wi-Fi link
behavior, real battery/thermal impact, or the real DAT adaptive-bandwidth
ladder under actual physical-glasses conditions. Do not cite this run as
physical-glasses validation.

  - Resolution/FPS target (~504x896 @ ~15 FPS): not directly assessed by
    this handoff (no resolution/FPS-target figures provided); the received
    rate (0.81 fps) reflects the expected 1-in-30 sender throttle, not the

  - Backpressure drops: 0, as expected (no drop mechanism implemented this
    milestone).
  - Physical-glasses figures: **not applicable — deferred, no physical-glasses
    run has been performed.**
- What does this run show about the current strict sequential
  receive -> process -> ack path in `tower/routes/ws.py`? Not conclusively
  assessable from this handoff — no per-window latency-growth-over-time
  figures were provided, only qualitative "low latency/resource usage" for
  the run as a whole. The 856.882s window with 0 backpressure drops and no
  disconnects is a positive sign the sequential path held up, but a
  trend-over-time figure (does `receive_to_result_ms` creep up as the
  session progresses?) would be needed to actually settle whether
  latest-wins backpressure is warranted — that evidence is not yet in
  hand.
- **Next steps (not started, not V0.8):** run the same validation against
