# V0.9.1 — Experimental CV Lab: Stateful Depth Experiment + CPU/GPU Baseline: Design Spec

Status: Approved. Source of truth for the implementation plan.

## Context

V0.9 (Experimental CV Lab) is complete on master at `5ed66eb`, 79/79 tests
passing. It proved the module lifecycle end-to-end with two *stateless*
OpenCV experiments (`baseline`, `edge_detection`) and explicitly deferred
three things as its own non-goals: PyTorch/CUDA, GPU utilization
measurement, and the V0.8 lifecycle findings that stateless experiments
never actually exercise (event-loop lifecycle mismatch; resource cleanup
on load-succeeds-start-fails).

This spec is that deferred next step: one model-backed (stateful)
experiment in the same Experimental CV Lab module slot, a CPU baseline,
then a CUDA baseline on the Tower's RTX 5070, measured and compared.

**Naming note:** this is deliberately *not* called V1.0. `03-ROADMAP.md`
already defines V1.0 as "Generalize Module Registry (When Justified)",
triggered only by a second *production* module — not by another
Experimental CV Lab experiment. `docs/modules/EXPERIMENTAL-CV.md` already
lists "a GPU-accelerated variant of an existing experiment, benchmarked
against its CPU baseline" as a normal candidate experiment inside the
existing sandbox, requiring no new roadmap milestone number. This work
stays inside the V0.8 module container's one hardcoded slot, selected via
the existing `TOWER_CV_EXPERIMENT` config pattern — hence "V0.9.1," a
continuation of the Lab, not a new milestone.

Confirmed before designing:
- Tower hardware: RTX 5070 (Blackwell, `sm_120`), driver reports CUDA
  13.2 support. No PyTorch installed in `.venv` today.
- `Module.mark_failed()` (`tower/modules/base.py`) only sets state —
  never calls any release hook. Confirmed leak path: a model loaded in
  `_do_load()` is never freed if `_do_start()` subsequently fails.
- `ModuleContainer.process()` (`tower/modules/container.py`) catches
  *any* exception from `module.process()` and permanently marks the
  module `FAILED` — confirmed via `test_process_exception_marks_failed_
  and_stops_further_processing`, which asserts a second `process()` call
  short-circuits without ever reaching the module again.
- `tower/experiments/__init__.py`'s `EXPERIMENTS: dict[str, Callable]`
  registry is for pure stateless functions specifically — no experiment
  in it allocates a resource, by design (see V0.9 spec).

## Hard gate: PyTorch/CUDA verification spike

Before any model code is written, run a verification spike on the actual
Tower machine and record the results in this repo. This blocks
Phase 1 below — if it fails, implementation stops and escalates rather
than proceeding with an unverified GPU path.

`scripts/verify_cuda.py` (new):

```python
"""One-shot PyTorch/CUDA verification for this Tower machine.

Run manually once before implementing any model-backed experiment:
    .venv\\Scripts\\python.exe scripts/verify_cuda.py

Not part of the pytest suite -- this needs a real GPU and a real torch
install, neither of which the fast test suite may assume.
"""

import torch


def main() -> None:
    print(f"torch version: {torch.__version__}")
    print(f"torch CUDA runtime: {torch.version.cuda}")

    available = torch.cuda.is_available()
    print(f"cuda available: {available}")
    if not available:
        raise SystemExit(
            "CUDA not available to torch -- STOP. Escalate before "
            "implementing any CUDA-backed experiment."
        )

    device_name = torch.cuda.get_device_name(0)
    capability = torch.cuda.get_device_capability(0)
    print(f"device: {device_name}")
    print(f"capability: {capability}")

    a = torch.rand(4, 4, device="cuda")
    b = torch.rand(4, 4, device="cuda")
    result = (a @ b).sum().item()
    print(f"trivial matmul sum on cuda: {result}")


if __name__ == "__main__":
    main()
```

Required to pass before Phase 1 (below) begins:
- `torch.cuda.is_available()` is `True`.
- `torch.cuda.get_device_capability(0) == (12, 0)` (RTX 5070 / Blackwell).
- The trivial matmul executes and returns a real float without raising.
- The exact PyTorch build/index used to achieve this (e.g. which
  `--index-url` on pytorch.org's install matrix) is recorded in this
  repo (README and/or a short note in this spec's implementation plan)
  once known — not guessed here, since the correct cu1xx build is a
  live fact about pytorch.org's current release matrix, not something
  fixed by this document.

If this fails: do not fall back to "just use CPU" as a silent substitute
for the GPU baseline this milestone exists to produce. Stop and escalate
per the user's explicit instruction — a CPU-only result would not answer
the question this milestone asks.

## Non-goals (explicitly out of scope)

- Consuming the roadmap's V1.0 slot (see Context, above).
- TensorRT, CV-CUDA, DeepStream — no measurement yet justifies any of
  them; this milestone produces the first PyTorch CUDA baseline that a
  future decision would need to beat.
- `pynvml` / whole-GPU utilization monitoring — `torch.cuda.memory_
  allocated()`/`max_memory_allocated()` covers this process's own GPU
  memory accounting at zero new dependency cost.
- Any change to the WebSocket wire *shape* beyond what V0.9 already made
  additive (`result_value`/`result_label`/`stage_ms`) — the depth
  experiment populates the same fields, just with different content.
- Sending the full depth map (or any image) over the wire — a single
  scalar summary only, same as `edge_detection`.
- A generalized "stateful experiment" base class/plugin mechanism — this
  is the *first* stateful experiment; generalizing now would repeat the
  same premature-abstraction mistake the roadmap already avoided at the
  module-registry level. Revisit only when a second stateful experiment
  creates a real requirement to generalize against.
- Async/threaded inference, request queuing, or any new backpressure
  mechanism — see "Backpressure" below.
- `/health` schema changes — model load time and device are logged, not
  exposed via the API.
- Dataset-recording sessions, sensor-profile negotiation, World Builder,
  Translator, persistent memory, iOS changes.
- Fixing the event-loop lifecycle mismatch (see "Lifecycle changes"
  below — reassessed as still inert, not touched).

## Chosen approach

One new stateful `Module` implementation, `DepthEstimationModule`,
running MiDaS-small monocular depth estimation, selected via a new
`TOWER_CV_EXPERIMENT=depth` value and a new `TOWER_CV_DEVICE` setting
(`auto`/`cpu`/`cuda`). It lives in the same V0.8 container slot as
`ExperimentalCVModule`, chosen by a small factory in `tower/main.py` —
not merged into `ExperimentalCVModule`'s stateless registry, and not a
second module slot (the container still holds exactly one module).

Three small, targeted lifecycle fixes land first, independent of the
depth experiment itself, because they're needed the moment *any* module
in this slot owns a real resource:

1. `Module._do_release()` — new sync hook, default no-op, called from
   `Module.mark_failed()`. Best-effort resource release on every FAILED
   transition, regardless of which lifecycle stage caused it.
2. `FrameProcessingError` / `FrameSkippedError` — a recoverable,
   frame-scoped failure no longer kills the whole module.
3. Event-loop lifecycle mismatch — reassessed, **left unchanged**. Model
   loading is synchronous CPU/GPU work with no loop affinity; the
   existing constraint ("lifecycle hooks must not create asyncio
   primitives") continues to hold and this experiment doesn't violate
   it. See "Lifecycle changes" for the full reasoning.

**Alternatives considered and rejected:**
- *Add depth as a third entry in the stateless `EXPERIMENTS` dict* —
  rejected: that registry's whole safety property (V0.8's deferred
  leak-on-partial-failure finding stays inert) depends on every entry
  being a pure function with no persistent resource. Forcing a stateful
  entry into it would silently break that invariant for the two existing
  experiments' shared code path.
- *Object detection or segmentation instead of depth* — rejected per the
  brainstorming discussion: weaker/no direct tie to a documented platform
  need (depth is explicitly named in `07-PLATFORM-CONSTRAINTS.md`
  Limitation 1 and `WORLD-BUILD.md`), heavier dependency/output surface.
- *Offload inference to a thread/executor now* — rejected: no
  measurement yet shows the inline synchronous call is a problem: only
  one glasses connection is expected under Rule 2, so there's no
  concurrent contention for the event loop today. See "Backpressure."

## Lifecycle changes

### 1. Event-loop lifecycle mismatch — reassessed, not fixed

`tower/main.py`'s `create_app()` runs `asyncio.run(module_container.
load_and_start())` — a throwaway event loop, separate from the one
`uvicorn` runs the app in afterward. This only matters if a lifecycle
hook creates a loop-bound object (`asyncio.Lock`/`Queue`/a background
`asyncio.create_task()`). `DepthEstimationModule._do_load()` calls
`torch.hub.load(...)` and `.to(device)` — synchronous, loop-agnostic
work. CUDA context creation is process-wide, not loop-bound. The
existing constraint carries forward unchanged: **lifecycle hooks in
this module must not create asyncio primitives.** Rewriting the
`create_app()`/`lifespan` wiring now would be real risk (it was already
amended once during V0.8 to keep `TestClient` compatibility) for a
problem this experiment doesn't actually have.

### 2. Resource cleanup on load-succeeds-start-fails — fixed

`tower/modules/base.py`:

```python
class FrameProcessingError(Exception):
    """Raised by a module's _do_process() to signal a recoverable,
    frame-scoped failure (e.g. an undecodable frame). ModuleContainer
    treats this as "drop this one frame" -- it must NOT take the whole
    module down. Any other exception from _do_process() is still a
    genuine module failure and still marks the module FAILED.
    """


class ModuleUnavailableError(Exception):
    """Raised by ModuleContainer.process() when the module cannot accept
    observations (not ACTIVE, or just failed)."""


class FrameSkippedError(ModuleUnavailableError):
    """A ModuleUnavailableError specifically because one frame failed a
    recoverable, frame-scoped check -- the module itself is still ACTIVE
    and will accept the next frame. Callers that only care "was this
    frame dropped" can keep catching ModuleUnavailableError unchanged;
    callers that want to distinguish "one bad frame" from "module died"
    (e.g. metrics) can catch this subtype specifically.
    """
```

`Module.mark_failed()`:

```python
def mark_failed(self) -> None:
    self._state = ModuleState.FAILED
    try:
        self._do_release()
    except Exception:
        logger.exception(
            "module %s: _do_release() raised during FAILED transition",
            self.descriptor.id,
        )
```

`Module._do_release()` (new, alongside the existing five abstract hooks,
but **not** abstract — default no-op so every existing module needs no
change):

```python
def _do_release(self) -> None:
    """Best-effort synchronous resource release on a FAILED transition.

    Default no-op. Override for a module holding a resource (e.g. a
    loaded model) that must not survive FAILED, regardless of which
    lifecycle stage caused it. Must not raise. Must be safe to call
    even if _do_load() only partially completed. Deliberately
    synchronous, not async: mark_failed() can be reached from
    ModuleContainer.process(), a synchronous hot-path method with no
    running event loop to await against.
    """
    return None
```

This single change covers every existing `mark_failed()` call site in
`ModuleContainer` (load/start failure, stop-timeout, unload-timeout,
process-exception) with no changes to `container.py` itself required
for this piece.

`DepthEstimationModule._do_release()` overrides it to drop the model
reference and call `torch.cuda.empty_cache()` when applicable (see
Components, below).

### 3. Bad frame → permanent FAILED — fixed

`tower/modules/container.py`, `process()`:

```python
def process(self, raw_bytes: bytes) -> Any:
    if self._module.state != ModuleState.ACTIVE:
        raise ModuleUnavailableError(
            f"module {self._module.descriptor.id} is {self._module.state}, not ACTIVE"
        )
    try:
        return self._module.process(raw_bytes)
    except FrameProcessingError as exc:
        logger.warning(
            "module %s: frame-level failure, module stays ACTIVE: %s",
            self._module.descriptor.id,
            exc,
        )
        raise FrameSkippedError(
            f"module {self._module.descriptor.id} could not process this frame"
        ) from exc
    except Exception as exc:
        logger.exception(
            "module %s raised during process(); marking FAILED",
            self._module.descriptor.id,
        )
        self._module.mark_failed()
        raise ModuleUnavailableError(
            f"module {self._module.descriptor.id} failed while processing"
        ) from exc
```

`FrameProcessingError` must be caught before the bare `Exception` clause
(subclass-before-superclass ordering already implied, but explicit
since `FrameProcessingError` does *not* subclass `ModuleUnavailableError`
— it's the internal signal from inside a module; `FrameSkippedError` is
the external signal the container raises in response).

This only whitelists specific, recognized per-frame failure modes (the
depth experiment raises it for one thing: an undecodable frame — see
Components). An unrecognized exception (a real bug, a CUDA OOM, a shape
error nobody anticipated) still propagates as a bare exception and still
correctly kills the module — this is a deliberate whitelist, not a
blanket exception swallow.

`tower/routes/ws.py`: needs exactly one small addition — catch
`FrameSkippedError` before the existing `ModuleUnavailableError` clause,
to record the new `frame_processing_errors` counter (see Components).
Everything else in `_handle_frame_message` is unchanged: a
`FrameSkippedError` still triggers the same log-and-drop path as any
other `ModuleUnavailableError`, since it *is* one.

### `tower/experiments/depth.py` (new)

```python
import cv2
import numpy as np

from tower.experiments import ExperimentResult
from tower.instrumentation import StageTimer
from tower.modules.base import FrameProcessingError


class DepthEstimation:
    """Stateful monocular depth estimation (MiDaS-small).

    Deliberately NOT registered in tower/experiments/__init__.py's
    EXPERIMENTS dict -- that registry is for pure stateless functions.
    This holds a loaded model across frames, so DepthEstimationModule
    owns an instance directly instead.

    Output is relative (inverse) depth, not metric distance -- MiDaS-
    small does not produce metric output. result_label says "relative"
    explicitly; treat as model inference, not measurement, per
    07-PLATFORM-CONSTRAINTS.md Limitation 1 / Core Principle 2.
    """

    def __init__(self) -> None:
        self._model = None
        self._transform = None
        self._device = None

    def load(self, device: str) -> None:
        import torch  # local import: torch is an optional [ml] extra;
        # nothing outside a depth-selected module may require it.

        self._device = torch.device(device)
        self._model = torch.hub.load("intel-isl/MiDaS", "MiDaS_small")
        self._model.to(self._device)
        self._model.eval()
        self._transform = torch.hub.load(
            "intel-isl/MiDaS", "transforms"
        ).small_transform

    def release(self) -> None:
        if self._device is not None and self._device.type == "cuda":
            import torch

            torch.cuda.empty_cache()
        self._model = None
        self._transform = None
        self._device = None

    def run(self, raw_bytes: bytes) -> ExperimentResult:
        import torch

        timer = StageTimer()

        with timer.stage("decode"):
            array = np.frombuffer(raw_bytes, dtype=np.uint8)
            image = cv2.imdecode(array, cv2.IMREAD_COLOR)
            if image is None:
                raise FrameProcessingError("undecodable frame")
            image_rgb = cv2.cvtColor(image, cv2.COLOR_BGR2RGB)

        with timer.stage("preprocess"):
            input_tensor = self._transform(image_rgb).to(self._device)

        with timer.stage("inference"):
            with torch.inference_mode():
                prediction = self._model(input_tensor)

        with timer.stage("postprocess"):
            depth = prediction.squeeze().detach().cpu().numpy()
            mean_relative_depth = float(depth.mean())

        return ExperimentResult(
            result_value=mean_relative_depth,
            result_label="mean_relative_depth",
            processing_ms=timer.total_ms,
            stage_ms=timer.snapshot(),
        )
```

Exact `torch.hub`/MiDaS transform call shape is confirmed against the
real API during implementation (TDD, real objects, no mocks per project
convention) — the sketch above is structural, not guaranteed-verbatim.

### `tower/modules/depth_cv.py` (new)

```python
from tower.experiments import ExperimentResult
from tower.experiments.depth import DepthEstimation
from tower.modules.base import Module, ModuleDataBehavior, ModuleDescriptor

DESCRIPTOR = ModuleDescriptor(
    id="experimental-cv",
    name="Experimental CV Lab",
    version="0.1.0",
    data_behavior=ModuleDataBehavior(
        persists_data=False,
        retains_raw_imagery=False,
        retention="none",
        supports_purge=False,
        transmits_externally=False,
    ),
)


class DepthEstimationModule(Module):
    """Runs the MiDaS-small depth experiment. Same descriptor id/name as
    ExperimentalCVModule -- from the platform's perspective this is
    still the one Experimental CV Lab slot, just a different backing
    implementation selected by TOWER_CV_EXPERIMENT=depth, same as
    switching between baseline/edge_detection doesn't change module_id.

    Stateful by design: this is the first Module in the Lab that
    actually exercises Module._do_release() (see
    2026-08-20-v0.9.1-depth-cv-baseline-design.md).
    """

    descriptor = DESCRIPTOR

    def __init__(self, device: str) -> None:
        super().__init__()
        self._requested_device = device
        self._experiment = DepthEstimation()

    async def _do_load(self) -> None:
        self._experiment.load(_resolve_device(self._requested_device))

    async def _do_start(self) -> None:
        return None

    def _do_process(self, observation: bytes) -> ExperimentResult:
        return self._experiment.run(observation)

    async def _do_stop(self) -> None:
        return None

    async def _do_unload(self) -> None:
        self._experiment.release()

    def _do_release(self) -> None:
        self._experiment.release()


def _resolve_device(requested: str) -> str:
    if requested == "cpu":
        return "cpu"
    import torch

    if requested == "cuda":
        if not torch.cuda.is_available():
            raise RuntimeError(
                "TOWER_CV_DEVICE=cuda requested but no CUDA device is available"
            )
        return "cuda"
    return "cuda" if torch.cuda.is_available() else "cpu"  # "auto"
```

An invalid `TOWER_CV_DEVICE=cuda` request on a machine without CUDA
raises inside `_do_load()` — caught by the existing `ModuleContainer.
load_and_start()` exception handling, correctly turned into `FAILED`.
No new failure mechanism needed.

## Backpressure — no action, decision rule recorded

Leaving `tower/routes/ws.py`'s sequential `receive → process → ack` path
unchanged, per the existing V0.7/V0.9 policy and because nothing here
demonstrates it's insufficient yet. Recorded explicitly because this is
the first milestone where the already-documented gap (`backpressure_
drops` stays 0; no drop mechanism exists) could actually become visible:
if measured CPU-path `processing_ms` for the depth experiment lands
meaningfully above the ~66ms/frame budget implied by a 15fps target,
`receive_to_result_ms` will grow session-wide with nothing shedding
staleness. **Decision rule, not action taken here:** if the benchmark
run (below) shows that, it is the trigger for a future frame-dropping
milestone — not something to build speculatively in this one.

## Performance measurements

Reusing `StageTimer`/`SessionMetrics` as-is:
- `StageTimer` stages for the depth experiment: `decode`, `preprocess`,
  `inference`, `postprocess` — same pattern as `edge_detection`.
- Model load time and resolved device: logged once at `_do_load()`
  completion (e.g. `"[Tower][Module] depth model loaded on cuda:0 in
  1234.5ms"`) — not added to `/health` or `SessionMetrics`; a one-off
  fact, not a per-frame or per-session series.
- GPU memory: `torch.cuda.memory_allocated()` / `max_memory_allocated()`
  logged alongside the existing periodic session summary
  (`SessionMetrics.should_log_summary()`) when the resolved device is
  `cuda` — zero new dependency (no `pynvml`), process-scoped (more
  accurate than whole-GPU tools for this purpose).
- `frame_processing_errors` (new `SessionMetrics` field, above) — the
  direct evidence that the "bad frame doesn't kill the module" fix
  actually holds in a real session.
- CPU-vs-GPU comparison is a **measurement run**, not a pytest
  assertion: `scripts/depth_benchmark.py` (new) drives the existing
  soak-script pattern (mirrors V0.7's `scripts/`) once with
  `TOWER_CV_DEVICE=cpu` and once with `=cuda` against the same input,
  and reports the `stage_ms_avg`/`processing_ms` figures from each
  run's session summary side by side. The first frame after a `cuda`
  load is excluded from the average (documented CUDA context first-init
  warmup cost, not representative steady-state latency).

Explicitly not built: dropped/skipped-frame *tracking beyond* the one
counter above, GPU utilization percentage, a metrics dashboard, or any
`/health` schema growth.

## Testing strategy

Same discipline as V0.8/V0.9: `.venv/Scripts/python.exe -m pytest`, real
objects, no mocks, TDD — with one addition specific to this milestone's
optional heavy dependency.

- `tests/test_module_base.py` — `Module._do_release()` default no-op;
  a fake module overriding it has `_do_release()` called exactly once
  when `mark_failed()` runs; a raising `_do_release()` is caught and
  logged, doesn't prevent the FAILED transition.
- `tests/test_module_container.py` — extend the existing fake-module
  pattern: a fake module whose `_do_process()` raises
  `FrameProcessingError` → `container.process()` raises
  `FrameSkippedError` (which `isinstance`-checks as `ModuleUnavailable
  Error` too) and the module **stays ACTIVE** for a subsequent call
  (mirrors, and is the direct counterpart to, the existing
  `test_process_exception_marks_failed_and_stops_further_processing`).
  A fake module's `_do_release()` is called when a load/start failure
  or a non-`FrameProcessingError` `process()` exception marks it FAILED.
- `tests/test_ws_experiment_fields.py` or a new
  `tests/test_ws_frame_skipped.py` — a fake module raising
  `FrameProcessingError` wired through `_handle_frame_message`:
