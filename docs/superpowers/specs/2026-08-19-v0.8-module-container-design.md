# V0.8 — Module Container / Library: Design Spec

Status: Approved. Source of truth for the implementation plan.

## Context

The tower currently has no module abstraction. `tower/routes/ws.py` calls
`tower/frame_processing.process_frame()` directly from the websocket frame
handler. `03-ROADMAP.md` V0.8 ("Minimal Module Container / Registry of One")
requires the tower runtime to host exactly one hardcoded module slot through
the full conceptual lifecycle (`UNLOADED/LOADING/READY/ACTIVE/STOPPING/FAILED`;
`load/start/process/stop/unload`) defined in `04-MODULE-SYSTEM.md`, without
building dynamic discovery, a registry, or descriptor negotiation.

Exit criterion (from the roadmap): the tower runtime can load, run, and
cleanly tear down one module through the full defined lifecycle.

## Non-goals (explicitly out of scope for V0.8)

- Dynamic module discovery / registry of more than one module.
- Descriptor fields the docs mark "should eventually" (`capabilities`,
  `sensorProfile`, `settingsSchema`, `uiExtension`) — sensor-profile
  negotiation is explicitly deferred until real DAT constraints are known
  (`02-DEVELOPMENT-RULES.md` Rule 4).
- Any real CV functionality (Experimental CV Lab is V0.9).
- Auto-recovery from `FAILED`.
- Any change to `tower/frames.py`, `tower/frame_processing.py`,
  `tower/metrics.py`, `tower/session.py`, or the stream_start/stream_stop
  measurement-window logic in `tower/routes/ws.py`.
- GPU/NVIDIA work of any kind.

## Chosen approach

App-scoped `ModuleContainer` wrapping the existing, already-tested
`process_frame()` as the one hardcoded V0.8 module. Module lifecycle is
driven once at Tower process startup/shutdown via FastAPI's `lifespan`, not
per-websocket-connection. The websocket frame handler changes by exactly one
seam: it calls `container.process(raw_bytes)` instead of `process_frame()`
directly.

Two alternatives were considered and rejected:
- Building the container without wiring it into the real frame path (decorative — exit criterion would only be true in tests, and duplicates the frame-processing path).
- Driving lifecycle per-websocket-connection (contradicts the documented "one server/runtime remains running while modules are swapped" architecture and Rule 8 resource discipline — a reconnect isn't a module switch).

## Components

### `tower/modules/base.py`

- `ModuleState(Enum)`: `UNLOADED, LOADING, READY, ACTIVE, STOPPING, FAILED`.
- `ModuleDataBehavior` (frozen dataclass): `persists_data: bool`,
  `retains_raw_imagery: bool`, `retention: str`, `supports_purge: bool`,
  `transmits_externally: bool`. Satisfies `04-MODULE-SYSTEM.md`'s
  requirement that every module descriptor declare its data behavior.
- `ModuleDescriptor` (frozen dataclass): `id: str`, `name: str`,
  `version: str`, `data_behavior: ModuleDataBehavior`.
- `Module` (ABC): `descriptor` (class/instance attribute), `state` property
  (starts `UNLOADED`), `async load()`, `async start()`,
  `process(observation)` (sync — hot path), `async stop()`,
  `async unload()`. Subclasses implement the four lifecycle hooks and
  `process`; the ABC (or container) enforces legal transitions.
- `ModuleUnavailableError`, `InvalidModuleStateError` exceptions.

State machine:
```
UNLOADED --load()--> LOADING --ok--> READY
                         \--fail/timeout--> FAILED
READY --start()--> ACTIVE
ACTIVE --process()--> ACTIVE   (only legal state for process)
ACTIVE --stop()--> STOPPING --ok--> READY
                         \--fail/timeout--> FAILED
READY --unload()--> UNLOADED
```

### `tower/modules/container.py`

`ModuleContainer`:
- Holds one `Module` instance (constructor arg — no registry).
- `async def load_and_start(self) -> None`: runs `module.load()` then
  `module.start()`, each under a bounded timeout
  (`asyncio.wait_for(..., timeout=LIFECYCLE_TIMEOUT_S)`). On timeout or any
  exception, catches it, sets the module to `FAILED`, logs truthfully, and
  **does not raise** — the Tower process must still boot and serve
  `/health`/`/ws` even if the one module fails to come up (mirrors
  `01-SYSTEM-ARCHITECTURE.md` Reliability Policies: "A module timeout must
  not crash the persistent tower runtime").
- `async def shutdown(self) -> None`: best-effort `module.stop()` then
  `module.unload()`, each bounded, logged, never raises.
- `def process(self, raw_bytes: bytes)`: if `module.state != ACTIVE`, raises
  `ModuleUnavailableError`. Otherwise calls `module.process(raw_bytes)`
  inside a try/except; on exception, sets the module to `FAILED`, logs it,
  and re-raises as `ModuleUnavailableError` so all subsequent frames are
  dropped without retrying a broken module (`04-MODULE-SYSTEM.md` Failure
  Behavior).
- `LIFECYCLE_TIMEOUT_S` is a module-level constant with a generous
  placeholder value; the docs are explicit that the exact figure is a
  future measurement decision, not fixed here.

### `tower/modules/baseline_cv.py`

`BaselineCVModule(Module)`: `process()` calls
`tower.frame_processing.process_frame` unchanged. `load`/`start`/`stop`/
`unload` are trivial (no model to load) but still go through the real state
transitions so the lifecycle is genuinely exercised, not stubbed out.

## Wiring

**Amendment (verified during planning):** `TestClient`, used exactly as all
existing tests use it (`client = TestClient(create_app())`, no
`with client:` wrapper), never runs FastAPI's ASGI `lifespan` startup/
shutdown events — confirmed empirically. Driving `load_and_start()` purely
through `lifespan` as originally written above would leave the module
`UNLOADED` in every existing test and break all frame-processing tests. Fix:

- `tower/main.py`: `create_app()` constructs the container
  (`ModuleContainer(BaselineCVModule())`, stored on
  `app.state.module_container`, same pattern as `app.state.session`) and
  then calls `asyncio.run(app.state.module_container.load_and_start())`
  **synchronously, before returning** — `create_app()` is the single choke
  point already called exactly once by production (`tower/main.py`'s
  module-level `app = create_app()`) and once per existing test, so this
  guarantees the module is `ACTIVE` (or truthfully `FAILED`) by the time the
  app exists, in both contexts, with zero changes to existing test files.
  `lifespan` is still registered on the app, but scoped to **shutdown
  only** — `yield` then `await app.state.module_container.shutdown()` —
  which real `uvicorn` always runs on clean process termination. Safe to
  call `asyncio.run()` inside `create_app()`: no test in this repo defines
  `async def test_...` or calls `create_app()` from a running event loop
  (verified — all tests are synchronous).
- `tower/routes/ws.py`: `_handle_frame_message` calls
  `websocket.app.state.module_container.process(frame.raw_bytes)` instead of
  `process_frame(frame.raw_bytes)`. On `ModuleUnavailableError`: log a
  warning (`"[Tower][Frame] #%s: module unavailable, frame dropped"`), do
  not send a `frame_result` for that frame, and do not record it into
  `SessionMetrics` (mirrors the existing `FrameError` handling — connection
  stays alive, no fabricated result, per `02-DEVELOPMENT-RULES.md` Rule 3).

## Concurrency note

FastAPI/Starlette runs a single websocket connection's receive loop as one
asyncio task; the existing `ws.py` loop already processes messages strictly
sequentially (one `await websocket.receive_json()` at a time, matching the
`receive -> process -> ack` path the V0.7 report describes). `ModuleContainer`
does not need its own locking for `process()` under the current execution
model — there is no concurrent access to a single module instance from
multiple frames in flight. Multiple simultaneous websocket connections (if
they ever occur) would call `process()` concurrently, but `process()` doesn't
mutate shared state beyond reading `module.state`, which is fine for
CPython's GIL-serialized single-threaded asyncio event loop. No lock is
added; if concurrent module reload during in-flight processing becomes real
(i.e., multiple modules or hot-swap), that is out of scope for V0.8's
single-module, load-once-at-boot design.

## Testing

- `tests/test_module_container.py`: full lifecycle with a fake in-test
  module (not `BaselineCVModule`, to isolate container logic); load
  timeout/exception → `FAILED`; `process()` raises `ModuleUnavailableError`
  when not `ACTIVE`; a `process()` exception marks the module `FAILED` and
  stops further routing.
- `tests/test_baseline_cv_module.py`: `BaselineCVModule.process()` produces
  the same `FrameProcessingResult` as calling `process_frame` directly
  (reuse the white/black-image fixtures already in
  `tests/test_frame_processing.py`).
- Full existing suite (currently 38 tests) must keep passing unmodified —
  this is the regression signal that `/ws` wire behavior is unchanged.
