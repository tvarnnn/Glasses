# V1.1 — Lifecycle Timeout Enforcement: Design

Status: **DESIGN — Revision 2.** Milestone: `03-ROADMAP.md` V1.1 (Module
Lifecycle Hardening), bounded-timeout half only. Scope of the module-switch
half is explicitly deferred — see Non-Goals.

> **Revision 2 (2026-08-21):** Revision 1 proposed `asyncio.to_thread` plus
> converting the four lifecycle hooks from `async def` to `def`. Review and
> direct measurement invalidated the mechanism and made the migration
> unnecessary. Both changes are corrected inline; §4 is substantially
> rewritten. Summary of what changed and why:
>
> 1. **`asyncio.to_thread` does not bound anything here.** `asyncio.run()`
>    joins the default executor at loop teardown, so the timeout fires but
>    `asyncio.run` does not return until the abandoned worker finishes.
>    Measured: a 2.0 s worker under a 0.3 s budget returned in **2.00 s**.
>    Since `create_app()` drives the load via `asyncio.run` at import
>    (`main.py:39,45`), Revision 1's headline claim — that a cold weight
>    download would be bounded — was **false**. A bare daemon thread
>    returned in **0.32 s** and did not delay interpreter exit. The design
>    now uses a daemon thread.

>    loop-blocking structurally impossible, but that protection comes from
>    the *offload*, not the signature: a hook running on a worker thread is
>    already off the event loop whether or not it is declared `async`.
>    Dropping the migration removes 17 hook rewrites across 7 files, avoids
>    permanently narrowing the contract (a future hook can still await real

>    found — where a single left-behind `async def _do_load` returns an
>    un-awaited coroutine and the module reports READY **without having
>    loaded**, a Rule 3 violation shipped by omission.
> 3. **Release deferral replaces the per-module invalidation token.** See
>    §4.3; it needs no cooperation from any module.

## 1. Recommendation pending user ruling (Master Guide §22)

The Master Guide classifies the synchronous-lifecycle-timeout gap as
"needs user judgment, not a silent autonomous patch" (`master-guide.md:274`,
`:588-589`), and `object-memory-first-slice.md:800-802` makes it a hard
`⛔ DECISION GATE`. This section records the ruling rather than burying it.

**Issue.** `ModuleContainer` advertises a bounded lifecycle timeout that it
cannot enforce against a synchronous blocking `_do_load()`.

**Evidence (measured, not assumed).** A module whose `_do_load()` calls
`time.sleep(3.0)` under a 0.5 s budget:

```
timeout was 0.5s; load_and_start took 3.00s
final state: ModuleState.ACTIVE
VERDICT: TIMEOUT NOT ENFORCED
```

Two facts make this worse than the docs record. The container does not
merely overrun the budget — it reports **`ACTIVE`**, i.e. success. And
*every* `_do_*` body in the entire codebase is synchronous; not one awaits
anything, so the `async` hook signature advertises a cancellability no
implementation has ever provided. The existing timeout tests all hang with
`await asyncio.sleep(999)` — a *cooperative* hang — so the suite passes
while the realistic case is untested (`testing-reliability-techdebt-audit.md:134-136`).

**Recommendation (NOT a ruling — see the blocked banner above).** Task 4's
**Option D → B, composed with E**: do V1.1 lifecycle hardening, fix the
contract centrally for all modules, and give `load` its own generous
timeout distinct from stop/unload.

Revision 2 corrects B's *mechanism*: the offload should be a bare daemon
thread, not `asyncio.to_thread`, because only the former actually bounds
the caller (§4.1). That correction strictly reduces scope — no module or
hook signature changes at all.

If the user rules for Option D→B+E, this spec is ready to plan against. If
the user prefers **C** (pre-provision weights, accept the gap) or **E+A**
(Object Memory local patch now, central fix later), the analysis in §4.3
about deferred release still applies and should be carried into whichever
option is chosen.

**Why this is not the escalation the docs feared.** Task 4's Option D is
literally "Defer Object Memory — do V1.1 lifecycle hardening first, then
build on the fixed contract. Cleanest ordering; costs the most schedule
time," and its recommendation closes with "Then **B** at V1.1, where
lifecycle hardening belongs and where depth can be migrated alongside"
(`:854-866`). The judgment call the docs reserved was a *schedule*
trade-off — patch locally to ship Object Memory now, versus fix the
contract first. This run's remit is roadmap continuation, which is exactly
the budget Option D says it costs. The caution was against "a silent
autonomous patch"; this is a reviewed spec and plan for the milestone that
owns the work.

**Alternatives considered.**

| Option | Rejected because |
|---|---|
| A — `to_thread` in one module only | Leaves `DepthEstimationModule` broken and the contract still trap-shaped. Task 4 itself routes A to B at V1.1. |
| B as literally written (`asyncio.to_thread`) | **Measured not to work.** `asyncio.run` joins the default executor at teardown, so the driver stays unbounded even though the state becomes truthful — 2.00 s against a 0.3 s budget. See Revision 2 note. |
| C — pre-provision weights, accept the gap | Converts an architectural requirement (`01-SYSTEM-ARCHITECTURE.md:93`) into an operational precondition. Rule 15 requires the runtime to bound the operation, not the operator to avoid triggering it. |
| E alone | Explicitly "not a substitute for A/B: alone it still cannot interrupt a synchronous call" (`:857`). |
| Post-hoc elapsed-time check, no threads | Simplest, and fixes the Rule 3 lie — mark FAILED if the call overran. Rejected as the *whole* answer because it leaves the driver unbounded: a wedged load still hangs `create_app()` forever, so requirement (i) "must not block indefinitely" is never met. Worth noting it is strictly better than `to_thread`, which costs concurrency hazards for the same non-result. |
| Subprocess isolation | The only mechanism that can truly *kill* wedged work. Large complexity, new failure modes, and no evidence yet demanding it. Recorded in §4.3 as the escalation if a real wedged-load incident occurs. |
| Do nothing / defer again | The gap is now load-bearing: it gates Object Memory Tasks 4–8, hence V1.2, hence V1.0/V1.1. |

**Cost if wrong.** Contained and reversible, and smaller after Revision 2:
the change is confined to `base.py`, `container.py`, `config.py` and one
line of `main.py`. **No module implementation changes and no hook signature
changes**, so the module contract every future module depends on is
untouched. Every behavior claim is pinned by tests. The one genuinely new
user-visible behavior — a slow load now FAILs instead of hanging — is
controlled by an env var and can be set arbitrarily high, so a bad default
is a config fix rather than a revert.

## 2. Requirements this must satisfy

Quoted from the documents that govern it:

- `01-SYSTEM-ARCHITECTURE.md:93` — "No lifecycle operation (LOADING,
  STOPPING, or equivalent) may block indefinitely. Each requires a bounded
  timeout. On timeout, the module transitions to a defined FAILED/unavailable
  state rather than hanging. **A module timeout must not crash the
  persistent tower runtime.**"
- `02-DEVELOPMENT-RULES.md:93` (Rule 15) — bounded timeouts with a defined
  failure transition; "Exact timing/queue constants are implementation
  decisions **informed by measurement**, not fixed by this rule."
- `prompts/TOWER-DEVELOPMENT.md:31` — core invariant: "lifecycle operations
  use bounded timeouts with a defined FAILED transition on timeout."
- Rule 3 (Truthful State) — never report readiness the runtime does not
  have. Reporting `ACTIVE` after blowing the budget is the current
  violation.
- Rule 8 (Resource Discipline) — release module resources no longer needed.
  This is what the abandoned-load leak violates.

## 3. Non-goals

- **V1.0 module registry / discovery / descriptor negotiation.** Not
  triggered: both selectable modules share `descriptor.id =
  "experimental-cv"`, so no second production module exists. Building it now
  is a Rule 10 violation, named as such in `object-memory-first-slice.md:118`.
- **V1.1's "exercised across real module switches" half.** There is no
  switch API; adding one requires the V1.0 registry. Left open, recorded in
  the roadmap. No new milestone number is invented (§22 reserves that).
- **`_do_process` execution model.** Still synchronous on the event loop.
  Corrected evidence (Revision 3): the relevant figure is **not** the
  baseline module's 0.46–0.64 ms/frame — this spec is about the depth
  module, which measured **`cv_processing_ms_avg: 29.102` on CPU**
  (`V0.9.1-depth-cv-baseline-report.md`), ~50× larger and blocking the
  event loop for the duration. At the 15 fps target that is ~44% loop
  occupancy, which is high but was measured without latency problems, so
  deferring is still correct — on the depth module's own numbers rather
  than a cheaper module's. Flagged as the next thing to revisit if a
  heavier module lands or the receive rate rises.
- **Object Memory itself.** Unblocked *by* this milestone, not built in it.
- **Auth / TLS / `0.0.0.0` bind.** Phase 1.5, and completing it requires the
  iOS client to send credentials.

## 4. Design

### 4.1 Hook signatures unchanged; the runtime runs them on a daemon thread

**No module changes at all.** The four hooks stay `async def`. `Module`
gains one private helper that runs a hook off the event loop on a bare
daemon thread and settles a future back on the loop:

```python
async def _run_hook(self, hook):
    loop = asyncio.get_running_loop()
    future = loop.create_future()

    def runner():
        try:
            asyncio.run(hook())            # hook's own loop, in this thread
        except BaseException as exc:
            self._settle(loop, future, exc=exc)
        else:
            self._settle(loop, future)
        finally:
            self._retire_hook()            # see 4.3

    threading.Thread(target=runner, daemon=True,
                     name=f"lifecycle-{self.descriptor.id}").start()
    return await future
```

`Module.load()/start()/stop()/unload()` stay `async` and keep owning state
transitions, so every `_state` write remains on the event loop thread. The
container keeps owning the timeout policy via `asyncio.wait_for`; the
daemon thread is what makes that `await` genuinely cancellable.

**Why a daemon thread and not `asyncio.to_thread`.** Measured, same 0.3 s
budget against a 2.0 s worker:

| Mechanism | `asyncio.run` returned | Interpreter exit |
|---|---|---|
| `asyncio.to_thread` | 2.00 s — **not bounded** | delayed |
| daemon thread | **0.32 s** | immediate |

`asyncio.run()` calls `shutdown_default_executor()` at teardown, which
joins outstanding worker threads (bounded only by
`asyncio.constants.THREAD_JOIN_TIMEOUT`, 300 s on this interpreter). A
custom `ThreadPoolExecutor` is no better: it registers an `atexit` join, so
interpreter exit still blocks. Only a thread that is never joined bounds
both. This matters at exactly the two places lifecycle is driven:
`main.py:39`'s `asyncio.run(load_and_start())` at import, and uvicorn's
runner calling `lifespan`'s `shutdown()` at exit — so this choice bounds
both startup **and** process exit.

**Why signatures stay `async`.** The protection this milestone needs comes
from the offload, not the signature — a hook on a worker thread is off the
loop either way. Keeping `async def` costs nothing and avoids: 17 hook
rewrites across 7 files; permanently losing the ability for a future hook
to await real async I/O; and the silent-failure mode where one missed
conversion leaves an `async def` hook returning an un-awaited coroutine
while the module reports READY without loading.

Consequence to document in the contract: a hook body runs in its own event
loop on a worker thread, so it must not touch asyncio primitives shared
with the main loop. Nothing in the repo does — verified, zero matches for
`asyncio.Lock|Queue|create_task` in module or experiment code — and it was
already a carried-forward constraint
(`2026-08-19-v0.9-experimental-cv-lab-design.md:421`). This design writes
it into `base.py` where implementers will actually see it.

Existing cooperative-hang test fakes (`await asyncio.sleep(999)`) keep
working unchanged and now complete in milliseconds instead of hanging: the
hook sleeps in its own loop on an abandoned daemon thread while the
container's `wait_for` fires on schedule.

### 4.2 Two timeouts, both configurable, defaults chosen from measurement

`load` is separated from the rest because its cost profile is different in
kind: it can legitimately download model weights.

| Setting | Env var | Default | Justification |
|---|---|---|---|
| Load | `TOWER_MODULE_LOAD_TIMEOUT_S` | **120.0** | **Unmeasured policy default, stated as such (Revision 3).** The measured numbers available are *warm* loads — 2141.4 ms CPU, 1617.8 ms CUDA (`V0.9.1-depth-cv-baseline-report.md:66,90`) — but this timeout exists to bound a *cold weight download*, for which this repo has no measurement at all. Anchoring on a 56× multiple of an unrelated quantity would be a policy choice dressed as a measurement (Rule 3). **Before implementation, measure the cold path**: clear `~/.cache/torch/hub`, time one `DepthEstimation.load("cpu")`, and set the default from that with margin. Until then 120.0 is a placeholder, not a finding. |
| Start / stop / unload | `TOWER_LIFECYCLE_TIMEOUT_S` | **10.0** | Unchanged from today's `LIFECYCLE_TIMEOUT_S`. These paths do no network I/O; `DepthEstimation.release()` is a local free. |

This also repairs a live defect: `ModuleContainer.__init__` accepts
`lifecycle_timeout_s` but `main.py:34` never passes it, so the default is
unconditionally in force and unconfigurable in production.

### 4.3 Abandoned lifecycle work: deferred release, not an invalidation token

`wait_for` bounds the *wait*, not the work: Python cannot kill a thread, so
a timed-out load may still complete and allocate a model afterwards.

Left alone this is Task 4's consequence 2, and `depth.py` shows it is worse
than a simple leak. `release()` reads `self._device` at `:79` to decide
whether to run the CUDA branch, while `load()` sets `_device` at `:46` and
assigns `_model` at `:51`. So releasing *concurrently* with a live load can:
skip `empty_cache()` entirely (if `_device` is still `None`), or null
`_device` between `:46` and `:52` so `_model.to(None)` runs. Then the worker
finishes and a FAILED module holds a complete model — on CUDA, GPU memory —
with no remaining release path, because `release()` already ran, `unload()`
is unreachable from FAILED (`base.py:107-110`), and `mark_failed()` will not
fire again.

The Object Memory gate proposed a per-module invalidation token
(`release()` sets `_invalidated`; `load()` checks it before assigning
`_model` — `:844-847`). **This design does something simpler and stronger:
never release concurrently at all.**

1. `Module` tracks whether a hook is in flight, guarded by a
   `threading.Lock` — the runtime's first lock, and the only shared state it
   protects is these two flags.
2. `mark_failed()` takes the lock. If a hook is in flight it sets an
   invalidation flag and **defers** release. Otherwise it releases
   immediately, exactly as today, so the existing `process()`-failure path
   is bytewise unchanged in behavior.
3. The worker thread, in its `finally`, takes the same lock, clears
   in-flight, and reads the invalidation flag. If set, it calls
   `_do_release()` — *after* the hook has returned, sequentially, on the
   thread that did the work.

The lock makes this race-free at the one dangerous instant (hook completing
just as the container times out): whichever party wins the lock, exactly
one release happens, never zero and never two.

Why this beats the token: `_do_release()` is now only ever invoked when the
hook is **not** running, so there is no concurrent-release hazard to reason
about, and **no module needs to change**. `DepthEstimation` is untouched, and
a future module inherits the guarantee instead of having to remember to
implement a token. It also removes the token's own subtlety — a partially
loaded resource still gets released, because release runs after the hook
unwinds either way.

Honest limit, to be recorded as a platform constraint and classified per
Rule 16: this **MITIGATES**. If the abandoned worker never completes — a
genuinely wedged socket rather than a slow one — its resources are never
reclaimed, and only process restart recovers them. Truly killable lifecycle
work REQUIRES subprocess isolation, which is out of scope here and should
be justified by evidence, not adopted speculatively. What this design does
guarantee is that the *runtime* stays bounded, responsive and truthful:
`FAILED`, serving `/health`, answering `module_unavailable` — which is
precisely `01-SYSTEM-ARCHITECTURE.md:93`'s "must not crash the persistent
tower runtime", not a promise of reclamation.

### 4.4 Resulting observable behavior

| Situation | Before | After |
|---|---|---|
| Sync load exceeding budget | Overruns silently, reports `ACTIVE` | Bounded; `FAILED`; `module_unavailable` to clients |
| Async (cooperative) hang | `FAILED` | `FAILED` (unchanged) |
| Fast load | `ACTIVE` | `ACTIVE` (unchanged) |
| Event loop during load | Blocked | Responsive |
| Cold weight download under 120 s | Hangs startup for its duration | Completes; `ACTIVE` (unchanged) |
| Cold weight download over 120 s, or wedged | Hangs startup **indefinitely**, no `/health`, no diagnosis | `create_app()` returns at 120 s; `FAILED`; `/health` serves |
| Process exit with lifecycle work outstanding | n/a | Not delayed (daemon thread is never joined) |
| Abandoned load finishes late | Model leaked, unreclaimable | Released by the worker after it settles |
| Abandoned load never finishes | Model leaked | Still leaked until restart — see §4.3 MITIGATES |
| Module fails in `process()` | `FAILED` + release | Unchanged |

## 5. Testing strategy

TDD. The headline regression test is the one the existing suite lacks: a
hook that blocks **synchronously**.

- Sync-blocking `_do_load` exceeding budget → `FAILED`, elapsed ≈ timeout
  not ≈ block duration, and state is never `ACTIVE`.
- The same for `_do_start`, `_do_stop`, `_do_unload`.
- Event loop remains responsive while a hook blocks.
- Abandoned load's late completion calls `_do_release()` exactly once.
- `_do_release()` is **not** called while the worker is still in-flight.
- `mark_failed()` with no in-flight work still releases immediately
  (regression guard on existing behavior).
- Load timeout and lifecycle timeout are independently configurable and
  independently honored.
- Config parsing: defaults, override, invalid value.
- Existing cooperative-hang fakes (`await asyncio.sleep(999)`) keep passing
  **unchanged** — proof that the contract is genuinely unbroken.
- `create_app()` itself returns within the load budget when the module's
  load blocks synchronously. This is the test Revision 1 would have failed:
  it asserts the *driver* is bounded, not merely that state is truthful.
- Process exit is not delayed by outstanding lifecycle work.
- Whole-suite guard: every `tests/test_ws*.py` stays green (Master Guide
  §23 names regressing the streaming path as a stop condition).

Test hygiene note: the three existing `sleep(999)` fakes should drop to a
short bounded sleep. Under the new design they no longer hang the suite,
but leaving 999-second daemon threads parked across a test session is
untidy and would mask a future regression in thread accounting.

## 6. Risks

| Risk | Mitigation |
|---|---|
| Introducing the runtime's first thread and first lock | Scope is deliberately tiny: the lock guards exactly two booleans, and `_state` writes stay on the event loop so the WS read path (`ws.py:53`, `container.py:81`) is unaffected. No module code changes. |
| A slow first load now FAILs where it previously (eventually) succeeded | 120 s default from measurement, plus an env override, plus a clear FAILED log naming the timeout. Documented in README. The intended trade: bounded-and-truthful beats unbounded-and-silent. |
| Daemon thread killed abruptly at interpreter exit while inside torch | Only reachable on the already-failed path, and the alternative measured worse (a 300 s exit delay). Noted as accepted. |
| Hook body runs in its own event loop | Verified nothing in the repo touches shared asyncio primitives; written into the `base.py` contract so implementers see it. |
| Abandoned daemon threads accumulate | Only one load occurs, at startup, with no retry loop. Recorded as a constraint to revisit when V1.0 adds module switching, which would make repeated loads possible. |

## 7. Follow-on work this unblocks

Object Memory's Task 4 decision gate largely dissolves: the contract is
fixed centrally, so Tasks 5–8 can be written against a lifecycle whose
timeout is real. Task 4 should be rewritten to record the V1.1 outcome
rather than re-litigate five options.
